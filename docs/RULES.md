# COC War Tool 规则与口径说明（RULES）

> 本文档是项目后续开发与优化的**标准依据**。所有统计口径、命名规范、边界处理
> 以本文档为准；修改口径必须先改本文档（及对应代码注释），再改实现。
> 关联代码：`domain/StatsCalculator.kt`、`data/csv/CsvImporter.kt`、
> `data/model/EventBuilder.kt`、`data/repository/WarRepository.kt`、`ui/util/Labels.kt`。

---

## 1. 游戏机制前提（来自游戏设定，不可违背）

| 机制 | 说明 | 影响 |
|------|------|------|
| 重复进攻不产新星 | 对**同一对手**重复进攻无法再获得胜利之星，每人最多从单个对手拿到 3 星 | 全队理论最大星数 = 我方人数 × 3（见 2.1） |
| 敌我人数相同 | 部落战/联赛对阵双方人数一致 | 理论最大星数可只用我方人数计算 |
| 部落战进攻槽位 | 每人 2 次进攻机会（2 槽） | 解析器按 2 槽补 unused 占位；个人单场最多 6 星（合法成就） |
| 联赛进攻槽位 | 每人每轮 1 次进攻机会（1 槽） | 解析器按 1 槽补占位 |
| 联赛结构 | 一场联赛含 **7 轮**，每月 **1~2 场**：月初 1 号场必有，月中场视游戏活动可能有 | SAABBCC C1C2 编码（见 3） |
| 星数来源 | 每颗星来自对单个对手的 3 星上限内的实际摧毁表现 | 星数以游戏原始数据 `total_stars` 为准，摧毁率不反推星数（见 4.6） |

## 2. 统计口径

### 2.1 满星率 `fullStarRate`

- **定义**：单场战报获得的总星数 ≥ 该场理论最大星数，即计为「满星」；满星率 = 满星场次 / 可评估场次。
- **理论最大星数 = 参与人数 × 3**（部落战与联赛**通用**，与进攻槽位数无关）。
- 依据：重复进攻同一对手不产新星，每人最多 3 星；敌我人数相同，全队理论最大 = 我方人数 × 3。
- **历史口径变更**：v3.4 曾用「槽位×3」（部落战=人数×6）；v3.5 改为「人数×3」；本版本
  以游戏机制理由再次确认「人数×3」为**最终口径**。
- 无成员数据（最大星数为 0）的场次不参与统计（`computeFullStarRate`，StatsCalculator.kt）。

### 2.2 三星率 `threeStarRate`

- **定义**：摧毁率 100% 的进攻次数 / **已使用进攻次数**。
- 分母为已使用进攻（`isUsed()` = 摧毁率 > 0），**不含** unused 占位槽。
- 展示位置口径统一：总览顶部卡片、战报情况表格（2.7）、成员数据、单场摘要。

### 2.3 进攻率 `attackRate` / `overallAttackRate`

- **定义**：已使用进攻数 / 理论可用进攻槽位数。
- 理论槽位按事件类型推算：部落战每人 2、联赛每人 1（`possibleAttackSlots`）。
- 解析器为未进攻成员补 `destruction=0` 占位记录，故占位计数与按类型推算一致。
- `overallAttackRate` 有 `coerceIn(0f, 1f)` 兜底；`computeTypeStats` 的 `attackRate`
  未 clamp（实际无越界场景，保留现状）。

### 2.4 未进攻判定

- 未进攻 = 该成员在本场**没有任何已使用进攻**（`attacks.none { it.isUsed() }`）。
- 解析器 `EventBuilder.build`（CSV 导入 / 样例数据共用）为缺失槽位**无条件**补
  `Attack(order, destruction=0)` 占位（部落战 2 条、联赛 1 条），所以「占位即未进攻」
  成立，`count { !it.isUsed() }` 可直接数出空槽数。
- **注意**：`possibleAttackSlots` 注释中「官方 API 无 unused 占位」描述的是**原始数据**；
  入库实体一律含占位。两处口径殊途同归，不可据此推断实体无占位。

### 2.5 本月最佳积分制 `computeTopMembers`（仅统计部落战）

| 规则 | 分值 | 计数项 |
|------|------|--------|
| 每获得一颗星 | +1 | `totalStars` |
| 每次 100% 摧毁率 | +1 | `threeStarCount` |
| 单场拿满 6 星（个人 2 槽×3） | +2 | `fullStarEvents` |
| 参战但空 1 个进攻机会 | -3 | `missedAttackCount` |
| 两次进攻全空 | -10 | `noAttackCount` |
| 名单成员未参与该场部落战 | -4 | `absentCount` |

- 评选范围 = 花名册成员 ∪ 参战成员（未参战的花名册成员也被计入扣分）。
  花名册即当前成员全集（离队直接删除，无离队态）；已删除的成员若其当期实际参战，仍按参战成员计入。
- 个人「单场满 6 星 +2」与部落「满星率（人数×3）」是**两个不同口径**：
  前者是个人 2 槽全拿满的成就奖励，后者是团队理论最大，互不冲突。
- 空槽数由占位记录推导（见 2.4），联赛不参与本评选。

### 2.6 成员月度星率 `starRate`（与满星率的区别）

- **定义**：`totalStars / (已使用进攻次数 × 3)`，即「每次进攻的得星率」，0~1 归一。
- 用于跨事件比较成员个人发挥（部落战/联赛可比），**不是**满星率，两者勿混用。

### 2.7 战报情况表格（统计页总览「战报情况」）

统计页总览在顶部卡片下方，以表格展示所选月份**逐场**战报数据
（`StatsCalculator.computeEventSummaries` → `EventStatSummary`），行按创建时间升序
编号 01、02…，点击行跳转对应战报详情页。列口径：

| 列 | 定义 |
|----|------|
| 总星数 | 该场战报获得的总星数（`clanTotalStars`） |
| 三星次数 | 摧毁率 100% 的进攻次数 |
| 使用进攻次数 | 摧毁率 > 0 的进攻次数（`isUsed()`） |
| 三星率 | 三星次数 / 使用进攻次数（同 2.2） |
| 参与率 | 使用进攻次数 / 可用总进攻次数 |

- **可用总进攻次数**：联赛 = 参与人数 × 1，部落战 = 参与人数 × 2
  （与 2.3 `possibleAttackSlots` 槽位推算一致，按**单场**成员数计）。
- **参与率即 2.3 进攻率的单场版本**：分子 = 已使用进攻数，分母 = 理论可用槽位，
  有 `coerceIn(0f, 1f)` 兜底（实际进攻数异常超过理论槽位时收敛到 1）。
- 三星率/参与率在表格中按阈值配色（三星率 50%/30%、参与率 90%/70%），仅展示层差异，非口径差异。

### 2.8 成员数据视图与联赛场次分组（统计页「成员数据」）

统计页原「排名」视图更名为「成员数据」，**部落战与联赛均可用**（联赛可选视图：
总览/成员数据/预警；本月最佳积分制仍仅部落战）。

- **排序固定**：按**参战次数降序**（并列次按三星率、场均摧毁），不再提供排序方式选择。
  参战次数 = 有已使用进攻的参战场次（`attacked`）。
- **部落战**：成员数据 = 所选月份全部部落战（与旧排名页一致）。
- **联赛**：不按整月聚合，按「月份 + 场次归属」分组统计，筛选对话框提供
  **月初场/月中场** 选择（仅显示该月实际存在的场次）。

**场次归属判定**（`parseLeagueMatchFromName`，与 3.2 C1C2 编码一致）：

| 名称 CC | 归属 |
|---------|------|
| `01..07`（C1=0） | 月初场 |
| `11..17`（C1=1） | 月中场 |
| 无法解析（非标准名） | **月初场**（统计页成员数据分组约定） |

- 归属无法解析的联赛事件**计入月初场组**（如示例数据「示例·15人联赛（第3轮）」）；
  此约定仅用于统计页成员数据分组，事件列表/赛季视图的联赛分组逻辑不变。
- **场次选择仅影响成员数据视图**：总览、预警、战报情况表格仍按整月统计（其余逻辑不变）。
- 选中月中场但当月不存在月中场事件时，自动回落到月初场（`recomputeForFilter`）。
- 成员数据行的逐场明细弹窗（`memberEventDetails`）同步跟随所选场次。

## 3. 事件命名规范 SAABBCC

格式：`S AA BB CC`（7 位），如 `0260801`、`1260803`。

| 位 | 含义 | 取值 |
|----|------|------|
| S | 类型 | `0`=部落战，`1`=联赛 |
| AA | 年份后两位 | `00..99` |
| BB | 月份 | `01..12` |
| CC | 部落战：当月第 N 场；联赛：C1C2 编码 | 见下 |

### 3.1 部落战 CC

- `CC = 当月第 N 场`（自增，上限 99，避免 7 位解析断裂）。
- 展示：`第X场`。

### 3.2 联赛 CC（C1C2 编码）

- CC 拆为两位：**C1 = 场次归属**（`0`=月初场，`1`=月中场），**C2 = 该场联赛第几轮（1..7）**。
- 合法值：`01..07` = 月初场第 1~7 轮；`11..17` = 月中场第 1~7 轮；其余值视为无法解析。
- 示例：`02680802` = 26年8月 月初场联赛第 2 轮；`12680913` = 26年9月 月中场联赛第 3 轮。
- **生成规则**（`generateEventName`）：C1/C2 自动推断——
  1. 本月无月初场轮次 → 月初场第 1 轮（CC=01）；
  2. 月初场未录满 7 轮 → 补其**最小空缺轮次**（按序导入即下一轮，CC=0X）；
  3. 月初场录满 → 开月中场第 1 轮（CC=11）；
  4. 月中场未录满 → 补其空缺轮次（CC=1X）；
  5. 两场都满（14 轮，理论不可能）→ 生成显式无效 CC=99 兜底（解析端视为无法解析）。
- 调用方传入的 `eventRound`（1..7 有效时）作为 C2 轮次提示，优先于自动推断。
- **解析规则**（`parseTypeAndRound` / `Labels.kt`）：C1 ∈ {0,1} 且 C2 ∈ 1..7
  才合法（CC ∈ 01..07 ∪ 11..17）；轮次 = C2，场次归属 = C1；名称不符合
  `S`/`AA`/`BB` 严格校验时同样视为无法解析，回退到实体字段/原始值。
- **历史数据说明**（两次语义变迁，均不可逆迁移）：
  - v3.9 及更早：联赛 CC = 当月第 N 场（自增），无场次/轮次语义；
  - v4.x 旧版：CC = 1..7 月初场、8..14 月中场（段偏移编码，`(cc-1)%7+1` 解轮次）；
  - 现版：CC = C1C2（十位场次归属 0/1，个位轮次 1..7）。
  旧数据在展示时可能被解读为新语义，属已知遗留。

### 3.2.1 旧编码 → 新编码迁移规则（工具页「数据迁移修复」）

- **迁移对象**：名称是合法 SAABBCC（S=1、年月合法）但 CC 不属于新合法集
  （01..07 ∪ 11..17）的联赛事件——即旧「当月第 N 场」或旧「段偏移」编码的历史数据。
- **映射算法**：按名称 AA+BB（年月）分组，组内按 `createdAt` 升序——
  前 7 个 → 月初场（CC=01..07，C2=序号）；第 8~14 个 → 月中场（CC=11..17）；
  溢出（>14 个）→ CC=99（显式无效，解析端回退，UI 显示原名，不丢数据）。
- **写入内容**：只重写 `eventName` 与 `eventRound`（=新 C2，溢出项 0），
  成员、星数、时间戳等一律不动。
- **安全约定**：迁移前必须先自动导出全量备份到应用私有目录
  `Android/data/<包名>/files/backups/migration_backup_*.zip`；
  备份写失败立即中止，不触碰任何数据；该备份可用「从备份导入」完整还原。
- 非标准名（如示例数据「示例·15人联赛（第3轮）」）不参与迁移。

### 3.3 展示文案

- 部落战：`第X场`
- 联赛：`月初场 第X轮` / `月中场 第X轮`（C1=0 → 月初场，C1=1 → 月中场）
- 轮次展示以实体 `eventRound` 字段为权威（保存时由名称 C2 解析回填），
  月初/月中从名称 C1 解析；无法确定时优雅降级（`leagueRoundLabel`）。

## 4. 数据与解析边界（历史决策沉淀）

1. **CSV 解析**：本软件数据格式统一为 CSV（无 JSON）；`CsvImporter.parse` 对缺失列、
   无法解析的数值按安全默认兜底（缺失列补 0、非法数值按 0），返回
   `ParseResult.Success/Error` 密封结果，不抛异常。
2. **进攻记录去重**：同一 `attack_order` 的多条记录只保留摧毁率最高的一条
   （防止重复记录导致 used 超槽）。
3. **同名去重**：重名玩家按 rank 顺序编号「原名」「原名1」「原名2」，保证主键唯一。
4. **成员主键**：`id = "$eventId#$index"`（index 而非 rank），避免重复 rank
   被 REPLACE 静默覆盖。
5. **备份恢复**（ZIP 多 CSV）：备份为 `coc_war_backup.zip`，内含 `events.csv` /
   `members.csv` / `roster.csv`；先全部校验解析成功才清空本地写入；仅含花名册的
   备份拒绝还原；花名册仅当备份明确含 `roster.csv` 时才替换。
6. **编辑不反推星数**（v3.9 决策）：编辑进攻摧毁率时**不**用启发式重算 `totalStars`，
   星数来自游戏原始数据（摧毁率无法可靠推导 1 星/2 星）。
7. **导出双程一致**：导出/备份 CSV 含 `rank` 字段，恢复后与源数据一致。
8. **数字格式化**：`"%.1f%%".format` 一律 `Locale.US`，避免区域设置产生小数点逗号。
9. **类型识别与切换**：CSV 导入按**当前选中类型**填充槽位（部落战 2 / 联赛 1），
   预览页可手动切换；战报未结束时部落战也可能被误判联赛，属已知局限。导入时切换
   部落战↔联赛会重新填充进攻槽位（2/1）并**重生成事件名**（不得只改前缀，部落战
   CC=场次序号与联赛 CC=C1C2 语义不同）。事件名自动生成按**名称 S 位**统计本月
   同类型事件（S 位是类型权威，不依赖实体 eventType 字段），避免字段与名称不一致时
   两类场次计数混淆。
10. **占位补全**：解析器为缺失槽位补 `destruction=0` 占位（见 2.4），
    这是未进攻统计与扣分的基础，**不得移除**。
11. **看不清标记 `-1`（v9）**：CSV 中 `-1` 是「看不清」哨兵值——总星数或摧毁率
    无法辨认时填 `-1`，导入链路（`CsvImporter` → `EventBuilder` → 导入预览）原样
    保留，不判越界、不猜测；导入预览检测到 `-1` 字段时弹二次确认，确认后按 0 入库
    （方案 A，库内不保留 `-1`，`totalStars`/`destructionPercentage` 均为非负）。
    `-1` 不参与部落总星数求和（`coerceAtLeast(0)`）、不参与摧毁率平均（`isUsed()>0`
    过滤）。
12. **导入 diff 预览**（B1）：导入预览展示成员汇总——总数 / 已在名单 /
    名单外新成员（保存时自动加入花名册）。名单外判定以「最终保存名」
    为准（成员匹配编辑后的名字）。
13. **CSV 编码**（B2）：全部 UTF-8；导出文件以 BOM（`\uFEFF`）开头，
    保证 Excel/WPS 直接打开中文不乱码。单元格含逗号/引号/换行时按 RFC 4180
    用双引号包裹并双写内部引号。
14. **CSV 全量导出格式**（B2，单文件多事件宽表）：
    表头 `事件名称,类型,时间,成员名,排名,职位,总星数,进攻1摧毁率,进攻2摧毁率`；
    部落战 2 列进攻、联赛第 2 列留空；时间格式 `yyyy-MM-dd HH:mm`。
15. **CSV 导入格式**（B2，单事件）：`成员名,排名,总星数,进攻1摧毁率[,进攻2摧毁率]`。
    摧毁率接受 `0..100` 纯数字或带 `%`；缺失列补 0；`-1` 为「看不清」标记（见 §4.11）；
    首行若无法解析出任何数字列视为表头跳过；导入按当前类型填充槽位（部落战 2 列/
    联赛 1 列），解析与保存共用 `EventBuilder` 完整链路（去重/占位/职位映射）。
    **外部识别 + 提示词**（v9 起，App 不含 AI 调用）：App 不再调用任何视觉模型，
    改为提供提示词：导入页右上⧉ / 设置 → 识别提示词，由 `data/ocr/OcrPrompts`
    按当前花名册动态生成（注入在册名单 + 形近名提醒 + 赛事模式），
    强制输出与本节完全一致的 CSV（去 `%`、未进攻 0、看不清 -1、联赛第 5 列留空）；
    用户把提示词与截图一起交给豆包等外部 AI，再把结果 CSV 粘贴/导入回来，
    经 `OcrCsvExtractor` 提取后走本节同一导入链路；`OcrValidation` 校验星数 0-6/
    摧毁率 0-100（`-1` 豁免），异常值仅提示人工核对、不阻断导入。
    **关键约束**：总星数与摧毁率是**独立观察值**——总星数直接抄图右侧数字，
    摧毁率来自左侧进度数字，二者无换算关系，禁止用摧毁率反推星数或反之
    （提示词设计与验证见 `docs/DOUBAO_OCR_VALIDATION.md` §8、§9）。
16. **月度报告 CSV**（B2）：口径全部复用 `StatsCalculator`（`computeMonthly`/
    `computeOverview`），只导出展示层已有结果，不引入新统计口径。
17. **花名册维护**（v7 起，v10 起改为「离队即删除」）：
    - **无离队态**：花名册 = 当前成员全集。确认离队 = **直接删除该行**
      （`RosterDao.delete`），不再保留 `active=false` 的离队行；
      删除后可用 Snackbar 撤销（连同职位一并还原）。
      `member_roster.active` 列保留以兼容旧库，业务代码不再读写；
      启动时 `WarRepository.purgeDepartedRows()` 会一次性清除旧版本遗留的离队行。
    - **成员更新**（花名册页「更多 → 成员更新」）：复制 App 生成的识别提示词
      （`RosterOcrPrompts`，注入当前花名册 + 易混名提醒）→ 到豆包等外部软件识别
      游戏内「部落 → 成员」页截图 → 粘贴结果 → 差异预览**逐人勾选**退出/新增 → 确认后硬替换。
      硬替换语义（`RosterDao.hardReplace`）：新名单 upsert，不在新名单的直接删除；
      取消勾选的「退出」成员会被保留，取消勾选的「新增」成员不会被加入。
    - **人数上限** 50（`domain/RosterLimit.kt`，COC 部落上限）：更新后超过上限时
      禁止确认并提示核对识别结果，不做静默截断。
    - **疑似离队筛选**（`RosterMaintenance.filterSuspectedDeparted`，纯函数）：
      花名册成员中，「连续缺席部落战场次 ≥ N」且「此前至少参战过一场」
      （缺席场次 < 部落战场次总数）者入选；从未参战的新成员不误报。
      缺席口径与 2.4 的连续缺席一致（只统计部落战，参加但未进攻算参战）。
    - **阈值 N**：默认 3，范围 1..10，可在「疑似离队清理」弹窗内调整并持久化
      （`coc_war_prefs` 键 `suspect_depart_threshold`）。疑似名单只作提示，
      **是否移出花名册最终由用户逐人手动确认**，系统不做自动删除。
    - **备份兼容**：备份 roster.csv 仍含 `在册` 列；还原时**丢弃** `在册=0` 的离队行，
      只还原当前成员（与「离队即删除」语义一致）。

## 6. WebDAV 同步口径（B3，双向同步）

- **同步模型**：本地全量数据（events + members + roster）与远端备份文件
  `coc_backup/coc_war_backup.zip` 双向同步，基于**数据指纹**判定变更：
  指纹 = 导出 ZIP（`exportAllData`）的 SHA-256，两端算法一致。
- **变更判定**：`localChanged` = 当前本地指纹 ≠ 上次同步时本地指纹；
  `remoteChanged` = 当前远端指纹 ≠ 上次同步时远端指纹。
  上次同步指纹持久化在本地（SharedPreferences）。
- **决策表**（`SyncDecider.decide`，纯函数）：

  | 本地 | 远端 | 上次指纹 | 动作 |
  |------|------|----------|------|
  | 无数据 | 无数据 | - | 两端一致，无需操作 |
  | 无数据 | 有数据 | - | 拉取远端恢复本地 |
  | 有数据 | 无数据 | - | 上传本地建立远端 |
  | 有数据 | 有数据，指纹相同 | - | 两端一致，无需操作 |
  | 有数据 | 有数据，指纹不同 | 仅本地变 | 上传本地覆盖远端 |
  | 有数据 | 有数据，指纹不同 | 仅远端变 | 下载远端恢复本地 |
  | 有数据 | 有数据，指纹不同 | 两端都变 | **冲突**：用户三选一（保留本地/采用远端/取消） |

- **覆盖保护**：被覆盖方**自动归档**，数据不丢——
  - 任何覆盖远端的动作（决策表「上传本地覆盖远端」、冲突时「保留本地」）在
    上传前先把远端旧版归档到 WebDAV `coc_backup/archives/coc_war_backup_<ts>.zip`；
  - 任何覆盖本地的动作（「下载远端恢复本地」、冲突时「采用云端」）先把本地旧版
    归档到应用私有目录 `files/backups/sync_backup_<ts>.zip`；
  - 本地记录归档名，超过 10 份自动删除最旧（WebDAV DELETE）。
- **冲突处理**：用户三选一（保留本地/采用远端/取消）；「取消」不改动任何一端，
  不更新指纹，下次同步会再次提示。
- **远端探测三态**：HEAD 探测 2xx=存在、404=不存在；服务器明确拒绝 HEAD（405/501）时
  回退到 `GET + Range: bytes=0-0` 轻量探测（只取状态码，不下载正文）；认证失败、
  网络错误、超时或其它非 2xx/404 响应一律视为「无法确认」，同步**立即中止**，
  不做任何写入、不更新指纹，避免把「不知道」当成「不存在」而覆盖有数据的远端。
- **手动兜底**：原「上传备份」「下载恢复」保留，语义为强制覆盖；
  完成后同样更新同步指纹，避免后续同步误判冲突。
- 同步失败（网络/校验）不修改任何一端数据，不更新指纹。
